## 1. 测试不是“多跑几次”

一个测试用例至少包含：给定输入、明确的期望输出、失败时能定位的断言。先写期望，再运行代码，能避免只挑对自己实现有利的样例。

边界来自契约。例如 `linear_search` 约定返回第一个命中下标，未命中返回 `-1`；那么重复姓名和不存在姓名都必须测试。`rank_records` 约定返回新列表，除排序结果外还要检查原列表未改变。

## 2. 最小但有区分度的用例

| 类别 | 示例 | 要验证什么 |
| --- | --- | --- |
| 空数据 | `[]` | 循环不执行也有定义明确的结果 |
| 单元素 | `[("阿青", 88)]` | 最小非空规模 |
| 重复命中 | 同名出现两次 | 返回第一个下标 |
| 未命中 | 查询不存在姓名 | 返回 `-1` |
| 相同排序键 | 两人同为 95 | 稳定排序保留原相对顺序 |
| 状态保护 | 排序前后检查原列表 | 函数不意外原地修改 |

Python 官方说明 `sorted()` 会建立新的已排序列表，而列表的 `sort()` 原地修改；Python 的排序是稳定的，相同键的记录保持原相对顺序。`assert` 适合今天的短小自检；项目变大后可把同样的契约迁移到 `unittest.TestCase`。

## 3. 可运行示例

```python
def linear_search(records, name):
    for index, (student, _score) in enumerate(records):
        if student == name:
            return index
    return -1


def rank_records(records):
    return sorted(records, key=lambda item: item[1], reverse=True)


def run_checks():
    assert linear_search([], "阿青") == -1
    assert rank_records([]) == []

    one = [("阿青", 88)]
    assert linear_search(one, "阿青") == 0
    assert rank_records(one) == one

    records = [("阿青", 88), ("小林", 95), ("阿青", 91), ("小周", 95)]
    assert linear_search(records, "阿青") == 0
    assert linear_search(records, "不存在") == -1
    assert rank_records(records) == [
        ("小林", 95), ("小周", 95), ("阿青", 91), ("阿青", 88)
    ]
    assert records[0] == ("阿青", 88)


if __name__ == "__main__":
    run_checks()
    print("python checks: OK")
```

运行：`python3 archive_day1.py`。本次已核对输出为 `python checks: OK`。

### 为什么这些断言有意义

- 空列表同时覆盖查找未命中和排序的最小规模。
- 重复姓名暴露“返回第一个还是最后一个”的歧义。
- 同分记录核对稳定性；只检查成绩序列无法发现同分顺序被打乱。
- 最后的原列表断言防止把 `sorted()` 误写成原地操作。

## 4. 复杂度与测试边界

`linear_search` 最坏检查全部 `n` 条，时间 O(n)，额外空间 O(1)。`sorted` 的具体实现无需手写复制；这里关注契约：返回新列表、稳定、按 `key` 取成绩。测试用例数量是常数，不改变被测算法的复杂度。

## 5. 易错点

- 只测“目标在中间”，没有测试空列表和未命中。
- 用集合比较排序结果，导致顺序错误也能通过。
- 只看输出，不检查输入是否被修改。
- 把 `assert function(...)` 当作通用检查；当合法结果为 `0` 或空列表时会误判。
